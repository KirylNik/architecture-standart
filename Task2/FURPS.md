| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F1  | Сайт и интернет-банк показывают список доступных депозитов с актуальными ставками |  |
| F2  | В интернет-банке клиент видит ещё и свои персональные ставки |  |
| F3  | На сайте можно подать заявку на депозит, указав номер телефона и ФИО |  |
| F4  | Заявка с сайта попадает в систему кол-центра. Менеджер кол-центра изучает её, звонит клиенту и может предложить особые условия |  |
| F5  | В интернет-банке клиент подаёт заявку на депозит, указав счёт и сумму |  |
| F6  | Клиент подтверждает заявку в интернет-банке СМС-кодом |  |
| F7  | Заявка из интернет-банка попадает в АБС, менеджер бэк-офиса депозитов согласует по ней ставку и условия в АБС | В MVP заявку обрабатывает бэк-офис, как и сейчас |
| F8  | Клиент получает СМС после того, как ставка подтверждена, и после открытия депозита |  |
| F9  | Ставки по депозитам ведутся в системе, а не в Excel. С ними работают сотрудники бэк-офиса депозитов и бэк-офиса кредитов | В задании предлагается делать это в АБС, вместе с согласованием ставки по заявке |
| U   | Удобство использования (Usability) |              |
| U1  | Новые экраны сайта и интернет-банка сделаны в дизайн-системе банка: привычные цвета и брендированные элементы |  |
| U2  | Заявку на депозит можно подать за несколько простых шагов, без визита в отделение и звонка | В задании: интерфейс должен быть максимально удобным для клиента. Здесь это требование сформулировано так, чтобы его можно было проверить |
| U3  | Интерфейс понятен пожилым клиентам: крупный шрифт, хороший контраст, подсказки на каждом шаге | Добавлено мной. Основные клиенты банка люди старшего возраста, и без этого часть из них пойдёт с вопросами в кол-центр |
| R   | Надёжность (Reliability)           |              |
| R1  | Все сервисы работают 24/7 |  |
| R2  | Доступность сервисов не ниже 99,9% | Команда интернет-банка считает это пока невыполнимым: всё работает в одном ЦОД на одной группе серверов. Сейчас простой на день не критичен, потому что клиентов в интернет-банке мало, но после запуска депозитов онлайн их станет больше |
| R3  | При сбое в ЦОД сервисы интернет-банка остаются доступными и выдерживают нагрузку | У банка есть резервный ЦОД, на него можно переключиться |
| R4  | В новом процессе интернет-банк не работает с АБС напрямую | База АБС уже перегружена, онлайн-заявки могут поставить под угрозу работу всего банка |
| R5  | Если АБС недоступна или перегружена, заявка клиента не теряется: она сохраняется и передаётся в АБС позже | Добавлено мной. Следует из R4: раз АБС нельзя нагружать напрямую, заявки нужно где-то накапливать |
| P   | Производительность (Performance)   |              |
| P1  | Операции на сайте и в интернет-банке отвечают не дольше 500 мс для 95% запросов | В задании: отклик должен занимать миллисекунды. 500 мс взял как проверяемую границу, цифру нужно согласовать с бизнесом |
| P2  | Справочные данные при платежах загружаются не дольше 500 мс | Сейчас они грузятся больше секунды, бизнес просит это исправить |
| P3  | Новые сервисы масштабируются горизонтально, запросы равномерно распределяются между серверами, приложениями и ЦОД | АБС так не умеет, см. ограничение про вертикальное масштабирование |
| P4  | СМС-код для подтверждения заявки приходит клиенту не позже чем через 30 секунд | Без кода клиент не подтвердит заявку (F6). Скорость доставки зависит и от телеком-оператора |
| S   | Поддерживаемость (Supportability)  |              |
| S1  | Для новых компонентов готовится документация, по которой систему можно будет расширять дальше |  |
| S2  | Новые функции интернет-банка дорабатывает команда банка, не меняя ядро подрядчика | СМС-функции сейчас в ядре, их доработка требует подрядчика, этого лучше избежать |
| S3  | Процесс заявок можно расширить без переделки: на автоматическое открытие депозита без бэк-офиса и на заявки на кредит | Добавлено мной. Это цель на год и следующий этап из планов банка |
| +R  | + Ограничения (Restrictions)       |              |
| +R1 | Данные клиента при передаче с сайта и в интернет-банке шифруются (HTTPS/TLS) | Требование к интерфейсам: с сайта приходят телефон и ФИО, в интернет-банке данные счёта |
| +R2 | При доработках в первую очередь используются технологии, которые уже есть в банке (MS SQL, Oracle). Новые допускаются, если они совместимы с текущими платформами разработки и в банке есть экспертиза хотя бы на уровне языков | Это и про поддерживаемость: чем меньше новых технологий, тем проще сопровождать |
| +R3 | Новый клиент проходит идентификацию лично в отделении. Поэтому полностью онлайн депозит в MVP может открыть только существующий клиент через интернет-банк | Банк не может принять нового клиента без личной проверки документов |
| +R4 | Если нужна очередь сообщений, используется Kafka | Текущая версия платформы интернет-банка с Kafka несовместима, это придётся учесть |
| +R5 | Интернет-банк можно переводить на микросервисы, но пока только в части открытия депозитов |  |
| +R6 | АБС масштабируется только вертикально | Так устроена её база данных. Нагрузку на АБС нельзя снять, просто добавив серверы |
| +R7 | Сотрудники бэк-офиса депозитов и бэк-офиса кредитов не видят данные друг друга | Требование безопасности из текущего процесса (задание 1). Важно для F2 и F9: персональная ставка зависит от кредитного риска клиента, а ставки ведут оба бэк-офиса |
| +R8 | Систему кол-центра могут дорабатывать Java-специалисты из команды АБС, без подрядчика | Платформа кол-центра расширяемая. Это пригодится для приёма заявок с сайта (F4) |
