### <a name="_3bfxc9a45514"></a>**Функциональные требования**

После запуска депозитов онлайн звонков станет больше, особенно от пожилых клиентов. Операторы должны называть актуальные ставки, а часть звонков при перегрузке уйдёт в партнёрский кол-центр. Партнёр работает в своей системе и готов принимать ставки только файлами. Решение опирается на MVP из ADR-1 (Task3): ставки уже ведутся в модуле АБС и через Kafka уходят в сервис депозитов.

- F1. Операторы кол-центра банка видят в своей системе актуальные ставки по депозитам и дату, на которую они действуют.
- F2. Ставки в системе кол-центра обновляются сами, когда их меняют в АБС.
- F3. Партнёрский кол-центр получает актуальные ставки файлом.
- F4. Файл обновляется после каждого изменения ставок и не реже раза в день.

### <a name="_qmphm5d6rvi3"></a>**Решение**

Диаграммы лежат рядом: контекст в `c4-context.png`, компоненты в `c4-component.png` (исходники в `.puml`). На диаграмме компонентов раскрыт новый сервис ставок внутри системы кол-центра.

Коротко: ставки уже уходят из АБС в Kafka. Кол-центр подписывается на них через новый сервис ставок, хранит копию у себя и показывает операторам. Тот же сервис после каждого изменения и раз в день собирает файл и кладёт его на SFTP-сервер, откуда его забирает партнёр.

Что меняется по системам:

1. АБС, сервис интеграции. Публичные ставки, без персональных, публикуются в отдельный топик Kafka. Кол-центр подписывается только на него и лишнего не получает (N3, +R7).
2. Система кол-центра. Новый сервис ставок на Java, Spring Boot со своей базой PostgreSQL. `RatesConsumer` читает топик и сохраняет ставки с датой (F2, N1). `RatesController` отдаёт их на рабочее место оператора, там появляется раздел «Ставки по депозитам» (F1). `PartnerExportJob` собирает CSV после изменения и по расписанию (F4, N2, N8), `SftpUploader` загружает файл на сервер (F3). Сервис отдельный, поэтому платформу подрядчика трогаем по минимуму, а если сервис упадёт, звонки принимать это не мешает (N5).
3. SFTP-сервер, новый, в DMZ банка. На каждого партнёра своя папка, вход по ключу, белый список адресов (N4). Сопровождает IT-отдел.
4. Партнёрский кол-центр. На своей стороне забирает файл по расписанию и показывает ставки операторам. От банка нужны формат файла и регламент.

Почему так:

- После MVP ставки уже лежат в Kafka. Брать их ещё раз из АБС незачем, нагрузка на АБС не растёт (N6).
- Сервис кол-центра на Java и с Kafka работает без проблем. Своя копия ставок даёт независимость: если сервис депозитов или интернет-банк недоступны, операторы всё равно видят ставки.
- Выгрузку для партнёра делаем в том же сервисе, потому что актуальные ставки уже у него. Источник один, и у своих операторов и у партнёра ставки совпадают.
- Файл, потому что партнёр готов только к файлам. SFTP, потому что он шифрует передачу и даёт нормально ограничить доступ.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

1. Кол-центр запрашивает ставки у сервиса депозитов по REST. Проще, подписка на Kafka не нужна, но если сервис депозитов лежит, операторы остаются без ставок, и кол-центр завязан на интернет-банк.
2. Кол-центр читает ставки прямо из АБС. Сделать быстро, но это лишняя нагрузка на АБС и доступ кол-центра к данным, которые ему не нужны (N6, N3).
3. Файл для партнёра собирает АБС ночной задачей PL/SQL. Нагружает и без того занятую команду АБС и её базу, а изменения в течение дня до партнёра не дойдут.
4. Отправлять партнёру ставки по почте в Excel. Разрабатывать ничего не надо, но нет контроля доставки, файл легко переслать дальше, и всё снова держится на людях.
5. Дать операторам партнёра доступ в систему кол-центра банка. Ставки всегда свежие, но партнёр работает в своей системе, а внешние учётки в системе банка это риск по безопасности.

**Недостатки, ограничения, риски**

1. У партнёра ставки могут отставать, он забирает файл по расписанию. В файле есть дата актуальности, а сроки забора фиксируем в договоре с партнёром.
2. Файл уходит во внешнюю компанию. Поэтому в нём только публичные ставки, а на SFTP пускаем по ключу и только с адресов партнёра.
3. Всё зависит от MVP: без модуля ставок, сервиса интеграции и Kafka из ADR-1 кол-центру неоткуда брать ставки. На роадмапе эти задачи идут раньше.
4. Система кол-центра принадлежит подрядчику. Обновление платформы может задеть раздел ставок на рабочем месте оператора, его придётся проверять при каждом обновлении.
5. Появляется SFTP-сервер, который нужно сопровождать IT-отделу.
